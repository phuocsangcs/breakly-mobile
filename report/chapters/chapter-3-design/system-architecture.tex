\subsection{Overall Architecture}
\label{sec:overall-architecture}

Breakly is a client--server system. The mobile client owns everything that
must keep working during a break: the countdown, the media players, the
in-app browsers and the local storage. The Spring Boot backend owns accounts,
the session history and streaks, the preferences, the curated content
catalogue and the proxies that fetch music and news from external providers.
The client talks to the backend only through a versioned REST API
(\texttt{/api/v1}). Pages that the user reads, watches or plays (articles,
YouTube and NYT Games) are loaded directly by the in-app browsers, and MP3
files are streamed or downloaded directly from Jamendo, so the backend never
relays media.

\subsection{Backend Architecture}
\label{sec:backend-architecture}

The backend is a layered Spring Boot application (package
\texttt{com.breakly}):
\begin{itemize}[leftmargin=1.8em,itemsep=2pt]
  \item \textbf{Controllers} (\texttt{AuthController}, \texttt{SessionController},
        \texttt{PreferenceController}, \texttt{ContentController},
        \texttt{GameController}) map HTTP requests to services and validate
        request bodies with Bean Validation.
  \item \textbf{Services} hold the business rules: registration and token
        rotation (\texttt{AuthService}), idempotent session upload and streak
        calculation (\texttt{SessionService}), the content catalogue and the
        music and news proxies (\texttt{ContentService}), and daily game plays
        (\texttt{GameService}).
  \item \textbf{Clients} wrap the external providers (\texttt{JamendoClient},
        \texttt{RssClient}, \texttt{YoutubeClient}) behind one shared HTTP client
        with strict timeouts. Their results are kept in a small in-memory TTL
        cache that returns the last good value when a provider fails.
  \item \textbf{Repositories} use Spring Data JPA; the schema is created and
        versioned by Flyway (V1 to V6), and Hibernate only validates it.
  \item \textbf{Cross-cutting parts}: Spring Security as an OAuth2 resource
        server that verifies the JWT on every protected request, CORS
        configuration, and a global exception handler that turns every error
        into the same JSON shape (Section~\ref{sec:api-contract}).
\end{itemize}

\subsection{In-App Architecture}
\label{sec:in-app-architecture}

The app follows a feature-based MVVM structure. Screens (views) live in
\texttt{src/app} as Expo Router routes and only render state. Each feature in
\texttt{src/features} (auth, session, preferences, music, news, video, games)
has an \texttt{api.ts} module for its endpoints, hooks or a Zustand store that
act as the view model, and its own components. Shared infrastructure lives in
\texttt{src/core}: the axios API client, which attaches the access token and
refreshes it once when a request is rejected with 401, the TanStack Query
client and query keys, key--value storage on AsyncStorage, secure token
storage and the media-focus coordinator that pauses music while the TV is
open. Reusable UI components from the Figma kit are in
\texttt{src/components/ui}, and the animated room (wall clock, window sky and
music notes) in \texttt{src/components/room}.

Two pieces of state are deliberately kept outside React components so that
they survive navigation: the session store, which runs the one-second tick and
computes the remaining time from the stored end time, and the music player
singleton, which keeps one \texttt{expo-audio} player for the whole app and
registers it with the iOS lock screen. Platform-specific behaviour is chosen
with file suffixes; for example \texttt{YouTubeBrowser.web.tsx} replaces the
native in-app browser with the curated embedded player when the app runs in a
web browser.
